# Multi-Agent Orchestration

## Summary

멀티 에이전트 오케스트레이션은 하나의 모델에게 모든 것을 시키는 대신 **역할별로 다른 모델·
도구를 배치하고, 그중 하나가 코디네이터 역할을 맡는** 구성이다. 원문 작성자가 '단일 모델
함정'이라 부르는 실패 — 하나의 채팅 창에서 하나의 모델이 모든 것을 하도록 밀어붙이는 방식 —
을 피하는 것이 출발점이다.

## Details

### 역할 분담

Reddit 사례의 스택은 다섯 계층으로 나뉜다.

| 계층 | 담당 | 역할 |
| --- | --- | --- |
| 오케스트레이터 | Hermes 에이전트 | 메모리·도구·예약 작업·메시징, 실제 컴퓨터 작업 수행 |
| 메인 에이전트 두뇌 | OpenAI Codex | 일반적인 앞뒤 조정과 도구 사용 |
| 코딩 전문가 | Claude Code | 제한된 범위의 코딩 작업 |
| 실행 환경 | 로컬 머신 | 파일·cron·이메일·셸·Home Assistant |
| 원격 인터페이스 | Telegram | 어디서든 시스템에 접근 |

작성자의 표현으로는 "Hermes를 관리자로, Claude Code를 전문가로, Codex를 메인 에이전트
두뇌로" 쓰는 구성이다.

### 워크플로

1. 사용자가 오케스트레이터에게 원하는 것을 말한다.
2. 오케스트레이터가 직접 처리할지, 코딩 부분을 전문가에게 위임할지 결정한다.
3. 전문가가 코드를 작성·검토·수정한다.
4. 오케스트레이터가 결과를 확인하고 간단한 테스트를 돌린 뒤 보고한다.

핵심은 4번이다 — 위임으로 끝나지 않고 오케스트레이터가 결과를 **검증**하고 시스템에 연결한다.

### 로컬 LLM 대안에 대한 판단

작성자는 Ollama로 로컬 모델을 시도했고, 기술적으로는 작동했지만 전체 에이전트 용도로는 너무
느렸다고 보고한다. 결론은 "작은 로컬 모델이 그 모든 것을 대체하게 만들려고 시간을 낭비하지
말고, 각 역할에 가장 적합한 도구를 쓰라"는 것이다. 이 판정은 작성자의 하드웨어 환경에 묶인
1인 경험이며 일반화된 벤치마크가 아니다. (inference / needs-update)

### 우아한형제들 사례와의 접점

기술블로그 글은 팀 하네스의 **확장 방향**으로 같은 구성을 지목한다 — 단일 AI에게 전부
맡기는 대신 역할별 하위 에이전트(sub-agent)에게 위임하거나, 작업 분기(fork)로 파이프라인을
병렬 처리하는 다중 에이전트 환경. 즉 Rules/Skills로 시작한 하네스가 도달하는 다음 단계와,
개인이 오케스트레이터 중심으로 조립한 이 스택은 같은 지점을 향한다.

### 도입 회고 — 6주 전환 사례

단일 에이전트에 조사·구현·검토를 전부 맡기던 구성에서 역할별 구성으로 6주간 전환한 사례는,
전환의 출발점이 성능이 아니라 **실패의 관찰 가능성**이었다고 보고한다. 한 창에서 모든 일이
벌어지면 어느 단계에서 틀어졌는지 사후에 짚을 수 없기 때문이다.

이 사례가 남긴 핵심은 역할 분리 자체보다, 역할 사이에 넘어가는 것을 계약으로 고정하는
쪽이었다 — 자세한 내용은 [[wiki/agent-delegation-contract|Agent Delegation Contract]] 참고.
쪼개기 기준도 같은 원문에서 나왔다: 독립적으로 검증 가능한 산출물이 나오는 단위까지만
쪼개고, 그보다 잘게 나누면 컨텍스트 격리의 이득보다 재설명 비용이 커진다.

### 댓글에서 나온 변형

- 에이전트 간 통신을 직접 구현하고, 항상 살아 있어야 하는 에이전트에는 세션을 시작·재개하는
  워커 서비스를 붙인 구성.
- 모델별 역할을 더 잘게 쪼갠 파이프라인 — 한 모델이 다음 청크를 정의하고, 다른 모델이 구현하고,
  더 빠른 모델이 리뷰한 뒤, 마일스톤 단위로 QA 검토를 한 번 더 도는 방식(TDD + 수직 슬라이스 원칙).
- 오케스트레이터의 스킬 시스템이 라우팅 패턴을 축적하면서 운영 시간이 길어질수록 빨라진다는 주장
  (댓글 의견, 측정 근거 없음 — inference).
