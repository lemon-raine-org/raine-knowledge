# Agent Delegation Contract

## Summary

에이전트 위임 계약은 [[wiki/multi-agent-orchestration|멀티 에이전트 오케스트레이션]]에서 상위
에이전트가 하위 에이전트에게 작업을 넘길 때, **넘기는 입력의 형식·돌려받을 산출물의 형식·
실패로 판정하는 조건** 세 가지를 위임마다 명시하는 규칙이다. 역할을 나누는 것만으로는
부족하고, 역할 사이의 경계 자체를 계약으로 고정해야 한다는 것이 회고의 결론이다.

## Details

### 왜 필요한가

역할별로 모델·도구를 나누는 전환 초기에 가장 많이 깨진 지점은 모델의 능력이 아니라
에이전트 사이에 넘어가는 것이 무엇인지 합의되지 않은 것이었다. 조사 담당이 요약문을
넘기면 구현 담당이 원문을 다시 읽는 식의 중복이 반복됐다.

### 계약의 3요소

1. **입력 형식** — 하위 에이전트에게 넘기는 데이터의 형태(원문 vs 요약 등).
2. **출력 형식** — 돌려받을 산출물의 형태.
3. **실패 판정 조건** — 언제 이 위임을 실패로 볼 것인가.

세 번째가 특히 중요하다고 보고한다. 실패 조건이 없으면 하위 에이전트는 무엇이든
그럴듯한 결과를 만들어 넘기고, 상위는 그것을 검증 없이 받는다.

### 역할 배치 사례

설계 회의에서 합의한 역할별 담당 범위·산출물·실패 판정 기준.

| 역할 | 담당 범위 | 산출물 | 실패 판정 |
| --- | --- | --- | --- |
| 오케스트레이터 | 작업 분해·위임·통합 | 작업 계획, 최종 보고 | 하위 산출물 통합 불가 |
| 조사 | 문서·코드 탐색 | 근거 목록(출처 포함) | 출처 없는 주장 포함 |
| 구현 | 코드 변경 | diff, 테스트 결과 | 테스트 미실행 또는 실패 |
| 검토 | 적대적 반증 | 반증 항목 목록 | 지적 0건 + 근거 없음 |

### 쪼개기 기준 — 컨텍스트 격리는 공짜가 아니다

에이전트를 나누면 각자의 컨텍스트가 깨끗해지는 대신, 같은 배경 설명이 여러 번 반복해서
들어간다. 역할을 잘게 쪼갤수록 총 토큰이 늘고 응답이 느려지는 구간이 있었다 — 이 중복
비용은 도입 초기에 과소평가됐다.

| 구분 | 기준 | 예시 소요(예시값) |
| --- | --- | --- |
| 쪼갠다 | 독립적으로 검증 가능한 산출물이 나온다 | 3~5단계 |
| 쪼개지 않는다 | 재설명 비용 > 격리 이득 | 1~2단계 |

### 핸드오프 실패의 회수

하위 에이전트가 실패했을 때 상위가 같은 작업을 그대로 재시도하는 것은 대개 무의미했다.
재시도 전에 실패 원인을 입력에 반영하지 않으면 같은 결과가 나온다. 정리된 회수 전략은
다음과 같다.

1. 실패 원인을 입력으로 되먹인다.
2. 한 번만 재시도한다.
3. 그래도 실패하면 사람에게 올린다.

## Open Questions

- 오케스트레이터 자신의 컨텍스트가 길어질 때 누가 그것을 압축할 것인가 — 원문은 다음 회의로
  이월된 미결 안건으로 남겼다.
- 역할 경계와 저장소(파일·디렉터리) 경계가 어긋날 때 어느 쪽을 따를 것인가.
- 에이전트 간 합의 실패를 사람 개입 없이 판정할 수 있는가.
- 실패 회수 재시도 상한을 1회로 유지할지는 4주 운영 후 재검토하기로 했다 — 검토 결과는
  아직 이 vault에 반영되지 않았다 (needs-update).
