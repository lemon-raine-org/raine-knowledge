# Agent Delegation Contract

## Summary

위임 계약은 에이전트가 다른 에이전트에게 일을 넘길 때 **넘기는 입력의 형식, 돌려받을
산출물의 형식, 실패로 판정하는 조건** 세 가지를 위임마다 명시하는 규칙이다. 역할을
나누는 것만으로는 부족하다는 관찰에서 나온다 —
[[wiki/multi-agent-orchestration|Multi-Agent Orchestration]]으로 전환한 회고는 초기에 가장
많이 깨진 지점이 모델의 능력이 아니라 "에이전트 사이에 넘어가는 것이 무엇인지 합의되지 않은
것"이었다고 적는다.

세 번째 항목이 계약의 무게중심이다. **실패 조건이 없으면 하위 에이전트는 무엇이든 그럴듯한
결과를 만들어 돌려주고, 상위는 그것을 검증 없이 받는다.**

> 출처 주의 — 이 노트의 근거 문서는 "지식관리 파이프라인 검증용 가상 샘플"임을 스스로
> 밝히고 있고 수치는 모두 예시값이다. 계약 구조는 패턴으로 쓸 만하지만, 기간·단계 수 같은
> 값을 실측 근거로 인용하면 안 된다. (needs-update: 실제 운영 데이터로 교체 필요)

## Details

### 계약의 세 항목

| 항목 | 명시하는 것 | 없을 때 생기는 일 |
| --- | --- | --- |
| 입력 형식 | 하위에게 넘기는 데이터의 모양 | 하위가 원문을 다시 읽어 상위 작업이 중복된다 |
| 산출물 형식 | 돌려받을 결과의 모양 | 상위가 결과를 통합하지 못한다 |
| 실패 판정 조건 | 무엇을 실패로 볼 것인가 | 그럴듯한 결과가 검증 없이 통과한다 |

입력·산출물 형식만 정하고 실패 조건을 빼면 계약이 성립하지 않는다. 형식은 맞는데 내용이
비어 있는 산출물이 정상 통과하기 때문이다. 이 실패 모드는
[[wiki/agent-context-optimization|Agent Context Optimization]]에서 전처리 스크립트의 출력
형식이 어긋났을 때 "에이전트가 조용히 빈 값을 채우는" 형태로 드러난다는 관찰과 같은 축이다.

### 중복 작업이라는 초기 증상

계약이 없을 때 먼저 드러나는 것은 오류가 아니라 중복이다. 회고가 든 예는 조사 담당이
요약문을 넘겼는데 구현 담당이 원문을 다시 읽는 상황이다. 산출물 형식이 합의되지 않으면
받는 쪽이 그것을 신뢰하지 못하고 스스로 다시 확보한다 — 역할을 나눈 이득이 그대로 사라진다.

### 역할별 계약 배치안 (사례)

같은 문서의 첨부(설계 회의 정리본)가 역할마다 계약 네 칸을 채운 예다. 원본이 화이트보드
스캔이라 OCR로 옮긴 표다.

| 역할 | 담당 범위 | 산출물 | 실패 판정 |
| --- | --- | --- | --- |
| 오케스트레이터 | 작업 분해·위임·통합 | 작업 계획, 최종 보고 | 하위 산출물 통합 불가 |
| 조사 | 문서·코드 탐색 | 근거 목록(출처 포함) | 출처 없는 주장 포함 |
| 구현 | 코드 변경 | diff, 테스트 결과 | 테스트 미실행 또는 실패 |
| 검토 | 적대적 반증 | 반증 항목 목록 | 지적 0건 + 근거 없음 |

검토 역할의 실패 판정이 이 표에서 가장 눈에 띈다. "지적 0건"을 그 자체로 실패로 보지 않고
**"지적 0건 + 근거 없음"**을 실패로 둔다 — 반증할 것이 정말 없었는지, 반증을 시도하지
않았는지를 가르는 것은 근거의 존재이지 지적 건수가 아니라는 판단이다.

### 핸드오프 실패의 회수

하위 에이전트가 실패했을 때 상위가 **같은 작업을 그대로 재시도하는 것은 대개 무의미하다**.
재시도 전에 실패 원인을 입력에 반영하지 않으면 같은 결과가 나온다. 회고가 정착시킨 전략은
세 단계다.

1. 실패 원인을 입력으로 되먹인다.
2. 한 번만 재시도한다.
3. 그래도 실패하면 사람에게 올린다.

재시도 상한 1회는 확정값이 아니라 회고 시점의 운영 기준이며, 원문 첨부의 미결 안건에
"4주 운영 후 재검토"로 남아 있다. (needs-update)
